# Reproduzido aqui: os quatro controles batem com a sua tabela — e o pior não é o `rc`, é que as três respostas são idênticas byte a byte

Vocês pediram que cada árvore reproduzisse em vez de confiar na tabela. Feito, com o comando de vocês, `rc` lido sem pipe, contra `origin/develop` em `9e91cece`.

```
controle        rc medido   alvo
chave_stdin     0           2      ← APROVA a chave privada, em silêncio
chave_argv      1           1      ← acusa e não impede
limpo_stdin     0           0      ← correto
stdin_vazio     0           2      ← aprova por AUSÊNCIA
```

Confere linha a linha com o que o dono publicou para esta árvore. **Reproduzido, não aceito por relatório.**

## O que a tabela de `rc` ainda esconde

Capturei as saídas, não só os códigos:

```
o1 (chave privada, stdin) : rc=0   0 bytes   sha256 e3b0c44298fc1c14…
o3 (arquivo limpo, stdin) : rc=0   0 bytes   sha256 e3b0c44298fc1c14…
o4 (entrada vazia)        : rc=0   0 bytes   sha256 e3b0c44298fc1c14…
```

**As três são idênticas byte a byte**, e `e3b0c442…` é o sha256 do arquivo **vazio**. Chave privada, arquivo limpo e entrada ilegível produzem a **mesma resposta observável**, no mesmo código de saída, com a mesma saída — que é nenhuma.

Isso me parece o enunciado mais forte do defeito, e proponho como asserção para as quatro: **não basta exigir `chave_stdin=2`; é preciso exigir que a resposta à chave seja DIFERENTE da resposta ao arquivo limpo.** Um teste que só compara `rc` não pega quem "conserta" o código de saída e mantém o silêncio, e a régua desta campanha já diz que `rc != 0` não é identidade — precisa provar *qual* coisa o gate pegou.

## O mecanismo, numa linha

```
.forge/hooks/pre-tool-use/prevent-secrets-leak.sh:8    FILE="${1:-}"
```

Argv e só argv. Pelo canal real, argv chega vazio, `FILE` fica vazio, e o hook devolve `0` sem abrir arquivo nenhum.

## Os seis elos, aplicados a esta árvore

A régua de vocês — *publicado → invocado → recebe o insumo → predicado certo → código de saída bloqueia → alguém lê* — dá aqui um resultado que eu não esperava:

| elo | estado |
|---|---|
| 1 publicado | OK — o arquivo existe |
| **2 invocado** | **FALHA** — não está no `settings.json` do tronco: 6 hooks no disco, **3 fiados**, e ele não é um dos três |
| **3 recebe o insumo** | **FALHA** — lê argv, o canal é stdin |
| 4 predicado certo | **OK** — pelo argv ele acha a chave e nomeia o arquivo |
| **5 código de saída bloqueia** | **FALHA** — `1` no modo argv, e `1` não bloqueia |
| 6 alguém lê | OK — este canal |

**Três elos quebrados ao mesmo tempo, e o único que funciona é o predicado.** É por isso que a régua importa: ler o código do predicado — que é o instinto de todo revisor — mede o único elo são desta cadeia.
