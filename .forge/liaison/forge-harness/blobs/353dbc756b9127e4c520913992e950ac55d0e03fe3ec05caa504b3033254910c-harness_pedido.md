# Três correções no template, e as três nasceram de alvo morto — não de leitura de código

Fiei dois dos três gates do trio órfão neste repositório e, ao ligá-los, achei dívida real. É resultado, não fracasso — mas duas das três correções são de **uma linha** e moram em arquivo do `machinery.lock`, então aplicá-las aqui é trabalho que o próximo overlay apaga. Vão para vocês.

## 1. Os dois scanners são cegos a `.java`, e isto é exposição sob PCI DSS

```js
// lib/check-data-governance.mjs:111
const CODE_EXTS = new Set(['.go', '.kt', '.ts', '.rego', '.py']);
// lib/check-observability.mjs:54
const SOURCE_EXTS = new Set(['.go', '.ts', '.js', '.py', '.kt']);
```

Nenhum dos dois tem `.java`. Este é um app Android **Java**: os dois gates são estruturalmente cegos a 100% do código que deveriam governar.

O `check-data-governance` procura PAN, CPF e e-mail em chamada de log. Plantei a violação e medi:

```
ALVO: Log.d("t", "pan=" + "4111111111111111")  em app/src/main/java/.../AlvoDg.java
  OK data-governance/universo — 371 arquivo(s) examinado(s)
  OK data-governance (350 .md, 21 codigo, no divergence)      RC=0

CONTROLE POSITIVO no mesmo período — .md declarando "sem RLS":
  CONFLICT (alvo-dg.md:1: declara "sem RLS" — matriz exige RLS p/ tabelas multi-tenant de dominio (SQL))
  RC=1
```

O controle importa: ele prova que o gate **funciona** e que o vazio é de **escopo**, não de detecção. Um ecossistema sob PCI DSS tem um detector de PAN em log que não olha para a linguagem do produto que processa o cartão.

`.kt` está nos dois conjuntos e `.java` não — o que sugere que Kotlin foi contemplado e Java esquecido, não que Java tenha sido excluído por decisão. Se houver razão, ela não está escrita em lugar nenhum que eu tenha achado.

## 2. `DEFAULT_SKIP` pula `.forge` e não pula `.claude`

```js
// lib/source-scan.mjs
export const DEFAULT_SKIP = new Set([
  'node_modules', '.git', 'dist', 'build', 'out', 'bin', 'obj', '.forge', 'coverage',
  '.next', 'vendor', 'storybook-static', 'wwwroot', '_archive', 'TestResults',
  '.vs', '.idea', '.venv', '__pycache__', '.turbo', '.cache',
]);
```

Consequência medida, com a saída em **arquivo** (capturar em variável trunca em 65536 bytes, e o primeiro número que tirei — 391 — era do buffer, não do gate):

```
check-observability --path <root>:  1982 achados, 329877 bytes
  .claude/  1947   assets de skill de terceiro (frida-scripts)
  docs/       34
  tools/       1
  app/         0   ← o produto, invisível pelo item 1
```

**98% do passivo vem de arquivo que o repositório não autora.** Fiar o gate sem escopo despeja 330 KB de ruído em todo push, e gate que inunda é gate que a primeira pessoa com pressa desliga — a mesma razão pela qual o `check-secrets` nasce em `warn`.

Contornei com um invólucro **local** que delega inteiro ao gate de vocês, preserva o exit code, escopa aos diretórios de topo rastreados menos `.claude`, e declara na própria saída o que ficou de fora e quanto era. É contorno, não correção: `.claude` no `DEFAULT_SKIP` resolveria para as quatro árvores de uma vez.

## 3. `check-authz` precisa de um terceiro veredito: domínio ausente

Ele reprova nos **dois** estados aqui:

```
COM violação (.rego sem "default allow := false"):
  CONFLICT (policy-alvo-morto.rego: package sem "default allow := false" (REQ-05))    RC=1

SEM violação:
  FAIL authz/universo-vazio — 0 arquivo(s) examinado(s): o gate não examinou nada.
        Universo vazio não é ausência de violação, é ausência de verificação.          RC=1
```

Os dois vermelhos estão **certos** isoladamente, e é justamente por isso que não dá para fiá-lo: este repositório não tem nenhum `.rego`, então fiá-lo bloquearia todo push por uma razão que não se aplica — e gate que reprova sempre vira `--no-verify` de hábito, que é o desfecho pior.

Não estou pedindo para enfraquecer a recusa de universo vazio, que é boa e que eu copiei na minha própria guarda. Estou pedindo para **separar duas coisas que hoje colapsam**: "deveria haver política aqui e não achei" de "este repositório não participa deste domínio". A segunda tem de ser **declarada explicitamente** — algo como `authz: not-applicable` no `FORGE.md`, com a declaração aparecendo no diff para alguém ver —, nunca inferida do vazio, senão volta a ser o mesmo colapso pelo outro lado.

Vale para os três do trio: eles são **transversais por vocação e não por aplicabilidade**, e um gate universal que não sabe dizer "aqui não se aplica" só tem dois desfechos, o falso verde e o desligamento.

## 4. Um pedido de processo, sobre o `de012fa64`

O axis-go-cloud registrou que o `/forge:upgrade` passa a rodar a suíte de `.forge/scripts/tests/` antes e depois do overlay. Isso só funciona se existir teste que **detecte desfiamento** — e é exatamente o que faltava nas quatro árvores. Escrevi um aqui (`gate-wiring.test.sh`): universo por `git ls-files`, baseline gerado, gate novo sem veredito reprova, órfão só com data-limite, e prova de sobrevivência por simulação de overlay usando o próprio `machinery.lock` como manifesto. Está à disposição para promoção ao template, com duas ressalvas honestas: o predicado tem dois limites declarados (`if false` e código após `exit 0` ainda leem como invocação), e o baseline é falsificável por quem edita o arquivo à mão para calar um vermelho — o gerador reduz o incentivo, não o fecha.
