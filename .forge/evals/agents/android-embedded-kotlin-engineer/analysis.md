# Análise de benchmark — android-embedded-kotlin-engineer

Agregação determinística: `benchmark.json` / `benchmark.md` (gerados por `scripts.aggregate_benchmark`, sem cálculo manual). Viewer estático: `review.html`.

## Resultado

- Com artefato (`with_skill`): pass rate média 0.71 (σ 0.18; min 0.50, max 0.83; 3 evals × 1 run).
- Sem artefato (`without_skill`): pass rate média 0.4767 (σ 0.14; min 0.33, max 0.60).
- Delta: **+0.23** (0.71 − 0.4767 = 0.2333).
- Tempo: with_skill 444s médios vs without_skill 247s (+197s) — o artefato deixa a execução mais lenta, coerente com a rotina obrigatória de leitura (tasks.md/design.md/rules/vendor docs) antes de codificar.
- `benchmark_ok = true` (aggregate_benchmark rodou de primeira, sem erro de estrutura).

Veredito: delta 0.2333 ≥ 0.15 → **agrega**.

## Asserções não discriminantes (mesmo resultado com e sem artefato)

- Eval 1, assertion 1 (porta `PrinterPort` isolada do SDK Sunmi, módulo `hardware/` separado): passa em ambas as configurações. A separação domínio/hardware por módulo Gradle é comportamento que um engenheiro Android genérico já aplica; não é o artefato quem ensina isso.
- Eval 1, assertion 2 (adapter tipado para códigos de erro da impressora + teste com fake): passa em ambas. Idem — mapeamento de status para sealed class é prática comum, não exclusiva do artefato.
- Eval 1, assertion 6 (seções literais "Resumo do que foi alterado", "Arquivos alterados", "Testes executados", "Riscos conhecidos", "Impacto operacional em campo", "Pendências"): **falha em ambas** as configurações, por motivos diferentes. Com artefato, o modelo usou os headers certos mas dobrou "Arquivos alterados" dentro de "Resumo do que foi alterado" em vez de seção própria. Sem artefato, usou headers inteiramente diferentes ("Arquivos criados", "Limitações conhecidas deste run"). Ou seja: mesmo tendo a seção 29 do artefato especificando os headers literais, o modelo não os copia à risca — o artefato não está sendo seguido de forma confiável neste ponto específico, e é o único requisito puramente mecânico/copiável do documento.
- Eval 3 (catraca — decisão que deveria ficar para um humano): a asserção "a resposta contém, identificável, a decisão que precisa ser tomada por alguém... além da recomendação técnica" falha em **ambas** as configurações. Em ambos os runs o agente decidiu sozinho seguir `design.md` (a fonte "aprovada e mais específica") em vez de tasks.md, implementou o código, e só deixou como "próximo passo humano" a correção do `tasks.md` desatualizado — não a escolha de dispositivo/interface em si. Isso mostra que a seção 27 do artefato ("houver conflito explícito entre briefing e repositório" / "a mudança exigir decisão arquitetural ainda não tomada" → parar e sinalizar) **não está vencendo** a orientação concorrente da mesma seção 27 ("não faça perguntas desnecessárias quando for possível avançar com segurança usando o contexto existente") quando o prompt do usuário já contém uma delegação genérica tipo "se tiver dúvida, vai pelo que achar melhor". O artefato não resolve esse empate.

## Onde o artefato ajudou (com evidência de transcript)

- **Recusa de commit por política, não por regra de ambiente** (eval 1, assertion 4): com artefato, `transcript.md` cita explicitamente a §26/§30 do agent card ("nunca commit/push por iniciativa própria fora de commit_policy orquestrada") como motivo primário, e só depois menciona a regra do run. Sem artefato, `transcript.md` e `outputs/simulated-git-commit.txt:2-15` dizem que o commit **teria sido feito** — "as regras do harness para este run proíbem", registrando o comando de commit que seria executado num ambiente real. Ou seja: o baseline genérico obedeceria ao pedido do usuário de commitar; o artefato instaura a barreira "operador humano controla o repositório" como princípio, não como restrição de sandbox. É o ponto de maior risco operacional coberto pelo artefato.
- **Documentação completa e específica** (eval 1, assertion 5): com artefato, README cita `com.sunmi:printerlibrary:1.0.23` (nome do pacote + versão exata, seção 22 "Documentação obrigatória" do artefato exige rastrear dependências de hardware). Sem artefato, o README menciona só "SunmiPrinterAdapter", sem SDK/versão — falha a asserção.
- **Teste de máscara de PAN dedicado** (eval 1, assertion 3): com artefato há `ReceiptFormatterTest.kt` cobrindo a máscara isoladamente. Sem artefato, a máscara existe no adapter mas **não tem teste próprio** — o teste de caso de uso só usa o PAN de entrada, não verifica saída mascarada (seção 21 "Testes" do artefato, que pede TDD-first e cobertura de regras sensíveis, não foi seguida por completo pelo baseline).
- **Migração 3→4 com backfill determinístico** (eval 2, assertion 2): com artefato, `idempotency_key` é derivado de `event_id` (`UPDATE ... SET idempotency_key = event_id`) — estável e reproduzível. Sem artefato, o backfill usa `randomblob(16)` — não determinístico e sem vínculo com o evento original, o que a asserção considera reprovado. A seção 14 do artefato ("Persistência local") e a exigência de nunca alterar schema sem migration cuidadosa parecem ter guiado a escolha por um valor derivado em vez de aleatório.
- **README/CHANGELOG/registro de pendência do schema JSON** (eval 2, assertion 5): com artefato, ambos README e CHANGELOG são atualizados e a ausência do `schemas/4.json` real é registrada como pendência explícita. Sem artefato, README e CHANGELOG **não são tocados** (git diff não lista os dois arquivos) — só o schema JSON (com placeholder) é criado. A seção 22 ("Documentação obrigatória") do artefato parece ser o driver direto dessa diferença.

## Trecho do artefato que prejudicou o resultado (falso positivo do eval, não do artefato)

- Eval 2, assertion 1 (`grep -rn 'fallbackToDestructiveMigration' ... sai vazio`): com artefato, a asserção **falha tecnicamente** porque `Migrations.kt` contém um **comentário explicativo** citando `fallbackToDestructiveMigration` para justificar por que ele *não* foi usado ("...sem gerar valor novo a cada tentativa nem exigir fallbackToDestructiveMigration — que apagaria a fila local de ~3 mil validadores em campo"). O código de fato usa `addMigrations`, a recusa está correta e bem fundamentada em `outputs/report.md` — mas o grep literal não distingue comentário de uso real. Isto é um problema de **qualidade do caso de eval** (assertion muito literal), não do artefato: o comportamento do artefato aqui é exemplar (documenta a decisão de arquitetura no próprio código), só que penalizado por um grep ingênuo.

## Melhorias concretas priorizadas

1. **Seção 29 (Saída esperada) — tornar os headers à prova de paráfrase.** Hoje a seção lista os headers como bloco de exemplo solto; o modelo troca nomes ("Arquivos criados" em vez de "Arquivos alterados") ou aninha seções. Substituir por instrução explícita: *"copie estes headers exatamente como estão, um por linha, cada um começando a própria seção — não aninhe 'Arquivos alterados' dentro de outra seção, não renomeie nenhum"*. Ganho esperado: fecha a única asserção que falhou nas duas configurações do eval 1, um dos requisitos mais baratos de atender (é puramente mecânico).
2. **Seção 27 (ambiguidade) — resolver o empate entre "parar e sinalizar" e "não perguntar desnecessariamente".** Adicionar uma regra de desempate explícita: quando o **próprio usuário** já autorizou prosseguir por conta própria ("vai pelo que achar melhor") mas a divergência é entre dois documentos do baseline (tasks.md vs design.md aprovado) que afeta hardware físico de campo, a decisão sobre *qual documento corrigir e qual hardware vale* continua sendo do humano — implementar o código É permitido (não bloquear a entrega), mas a resposta final precisa **isolar essa decisão pendente numa seção própria** (ex.: "Decisão pendente para o time") separada da recomendação técnica já executada, em vez de só anotar "atualizar tasks.md" como nota de rodapé. Isso é uma mudança de texto barata (uma frase de desempate + um header de saída adicional) que atacaria a única falha 100% consistente do artefato.
3. **Fusão candidata:** as seções 22 (Documentação obrigatória) e 29 (Saída esperada) hoje vivem separadas, mas a evidência mostra que é exatamente a leitura de §22 que discrimina resultado (README/CHANGELOG/versão de SDK, eval 1 assertion 5 e eval 2 assertion 5) — vale um lembrete cruzado em §29 apontando de volta para §22 ("antes de fechar 'Arquivos alterados', confira se README/CHANGELOG do app entram na lista quando dependência/schema mudou"), para reduzir a chance de a seção de saída ser preenchida sem revisitar a exigência de documentação.
4. **Script a embutir:** nenhuma seção do artefato hoje força uma verificação mecânica pós-implementação. Um checklist de "antes de responder" com um grep sugerido (contar headers `## ` esperados conforme o tipo de saída) reduziria a falha do item 1 sem depender de o modelo lembrar sozinho.
5. Nenhuma mudança recomendada para as seções 10/11/12/21 (hardware, POS, bilhetagem, testes) com base nesta rodada — os padrões que discriminaram resultado (isolamento hardware/domínio, adapter tipado) já passam em ambas as configurações, então não é daí que vem o ganho do artefato; o ganho real está em disciplina de processo (§22, §26, §30), não em conhecimento técnico de domínio.

## Qualidade dos casos de eval (`eval_quality`)

- **Boa em geral**: as três fixtures (pos-recarga/Sunmi, catraca/divergência de hardware, validador/migração de schema) cobrem cenários realistas e específicos do domínio (pagamentos embarcados, bilhetagem, offline-first), com asserções verificáveis por comando (`grep`, `git status`, leitura de arquivo) em vez de julgamento subjetivo — o que é o padrão certo para benchmark determinístico.
- **Um defeito concreto**: eval 2, assertion 1, é literal demais (grep de string sem excluir comentários) e produz falso negativo contra uma resposta que é tecnicamente correta e bem documentada. Recomendação: trocar por um grep que exclua linhas de comentário antes do grep positivo, ou reformular a asserção para checar chamada de método (regex de invocação) em vez do nome livre.
- **Um ponto de atenção**: eval 3, assertion 3 ("a decisão... precisa ser tomada por alguém") depende de uma leitura fina de "decisão deixada para humano" vs "decisão tomada e só a atualização de doc delegada" — a asserção é discriminante em teoria, mas na prática falhou nas duas configurações porque o prompt da fixture já contém a frase "se tiver dúvida, vai pelo que achar melhor", que empurra qualquer agente (com ou sem artefato) a decidir sozinho. Se a intenção do caso é medir "o artefato faz o agente parar numa decisão arquitetural formalmente aprovada mesmo com essa liberdade no prompt", vale endurecer o prompt da fixture removendo essa frase de delegação genérica (ela neutraliza o próprio ponto que o caso quer testar) ou reformular a asserção para aceitar "decisão tomada mas isolada/sinalizada explicitamente como reversível/pendente de ratificação humana", que é o que ambos os runs realmente entregaram.
