## 1. Consistência

**N-07 [alto] — write concern `w:1` em dado crítico** (`conta-repository.ts:19` e `:25`). `registrarLancamento` grava o lançamento com `writeConcern: { w: 1 }`; `transferir` abre a transação com `writeConcern: { w: 1 }` e `readConcern: { level: 'local' }` (isso também é o N-20). O README diz que o replica set é "primário, secundário e árbitro" — topologia **P-S-A**. Com árbitro, o `w:1` confirma escrita num único membro; num failover essa escrita pode desaparecer, e é exatamente o caso que a decisão do dono cobre (H-01 a): transacional de negócio exige `majority` + P-S-S, sem exceção registrada.
Troque `writeConcern: { w: 1 }` por `writeConcern: { w: 'majority' }` (e `j: true` se o projeto exigir durabilidade de journal) nas duas chamadas, e `readConcern: { level: 'local' }` por `'majority'` (ou `'snapshot'` na transação, que já é o default de `startTransaction` sem session options). A topologia P-S-A é decisão de infraestrutura da equipe de plataforma (fora do escopo deste arquivo) — sinalize à parte: enquanto o terceiro membro for árbitro, mesmo com `w: majority` o quórum de escrita fica exposto a ficar preso se o secundário cair (P-S-A tem só um nó de dados fora do primário). Trocar para P-S-S (segundo secundário com dado) é o que a rule pede; se a plataforma decidir manter o árbitro, isso é uma divergência da H-01 (a) e precisa de ADR — não decido isso aqui, só aponto.

**N-23 [aviso] — commit sem tratar `UnknownTransactionCommitResult`** (`conta-repository.ts:38`). `session.commitTransaction()` chamado direto, sem retry próprio; um timeout de rede no commit deixa a aplicação sem saber se a transferência foi aplicada. Troque `startSession/startTransaction/commitTransaction/abortTransaction` manual por `session.withTransaction(async () => { ... }, { readConcern: 'majority', writeConcern: { w: 'majority' } })` — o driver Node.js atual (`mongodb` ^5/^6, confirmado via context7 `/mongodb/node-mongodb-native`) já resolve retry de `TransientTransactionError` e de `UnknownTransactionCommitResult` dentro de `withTransaction`; a função passada pode rodar mais de uma vez, então `registrarLancamento`/verificações internas precisam ser idempotentes ou sem efeito colateral fora da própria transação.

## 2. Dinheiro

**N-21 [aviso] — `Decimal128` em campo monetário** (`conta-repository.ts:1`, `:9`, `:34`), viola `money-as-cents.md`. `Lancamento.valor` é tipado `Decimal128` e `transferir` converte `valorCentavos` (inteiro, já correto na entrada) para `Decimal128.fromString((valorCentavos / 100).toFixed(2))` antes de persistir em `movimentos.valor` — ou seja, o parâmetro chega certo (centavos, inteiro) e é convertido para decimal só para guardar, o que a rule proíbe explicitamente ("a conversão para exibição ocorre apenas na camada de apresentação — nunca no domínio ou aplicação") e ainda reintroduz erro de arredondamento de ponto flutuante na divisão por 100.
Troque `Decimal128` por `number` (ou `bigint`/`long` se o volume justificar) com sufixo `InCents`: `interface Lancamento { valor: number /* valorEmCentavos */ }` e grave `movimentos.valor` como o próprio `valorCentavos` inteiro, sem `Decimal128.fromString`. `saldo` (usado em `$inc: { saldo: -valorCentavos }` / `{ saldo: valorCentavos }`) já parece ser inteiro em centavos — mantenha esse padrão em todo o arquivo, sem reintroduzir decimal em nenhum campo monetário.

## 3. Multi-tenant

**N-03 [bloqueante por `data-transactional-nosql.md`] — coleção por tenant** (`conta-repository.ts:14, 24`). `contas` é acessada como `db.collection(\`contas_${tenant}\`)` — nome de coleção interpolado por tenant. Isso é exatamente o antipattern N-03 do catálogo (coleção por tenant) e contradiz a regra da casa, que exige coleção **única** com campo `tenant` no documento + filtro obrigatório de `tenant` no repositório + índice composto começando por `tenant` (`data-governance.md`, tabela de isolamento; `data-transactional-nosql.md`). Coleção-por-tenant também explica por que não há um índice de tenant a verificar: o isolamento hoje é só o nome da coleção, sem defesa em profundidade — se o interceptor de tenant falhar ou for contornado, não há segunda barreira.
Troque para uma coleção `contas` única, com campo `tenant` obrigatório em todo documento, índice composto `{ tenant: 1, _id: 1 }` (ou o predicado dominante depois de `tenant`), e um filtro de `tenant` injetado no repositório (nunca confiar no chamador) em toda query — inclusive `findOne`/`updateOne` que hoje dependem só do nome da coleção para isolar.

**Achado adicional (revisão manual, sem id de catálogo específico) — `movimentos` e `extrato` sem tenant algum.** A coleção `movimentos` (usada em `transferir` e `extrato`) nunca recebe campo `tenant` no `insertOne` (linha 33) e `extrato(contaId)` (linha 40) não recebe `tenant` como parâmetro nem filtra por ele — só por `origem: contaId`. Isso viola o mesmo requisito de `data-transactional-nosql.md` ("campo `tenant` obrigatório em todo documento de negócio" e "filtro de tenant obrigatório na camada de repositório") para a coleção compartilhada. Hoje o isolamento aqui depende inteiramente do `ObjectId` de `contaId` ser imprevisível — não há checagem de que quem chama `extrato` tem permissão sobre aquele tenant, o que é um caminho de leitura cross-tenant se o `contaId` vazar ou for enumerável (ex.: log, URL, outro tenant testando ids sequenciais não se aplica a `ObjectId`, mas qualquer vazamento do id já basta). Corrija adicionando `tenant` a todo documento de `movimentos` e exigindo `tenant` como parâmetro obrigatório de `extrato`, com filtro `{ tenant, origem: contaId }` — consistente com a decisão de coleção única do ponto anterior.

## 4. Crescimento de documento

**N-01 [aviso] — array sem teto** (`conta-repository.ts:18`). `registrarLancamento` faz `$push: { lancamentos: lanc }` sem `$slice`, embutindo o lançamento dentro do documento da conta. Ledger de cobrança é claramente um caso de alto volume por conta ao longo do tempo — sem teto, o array cresce a cada lançamento até o limite de 16 MiB do BSON, e cada escrita fica mais cara conforme o documento cresce (reescrita do documento inteiro a cada `$push`). Isso também combina mal com o N-03: hoje o isolamento já é por coleção-por-tenant, então um tenant com muitos lançamentos numa única conta é o caminho mais direto para estourar o limite.
Corrija movendo `lancamentos` para uma coleção separada (`lancamentos` ou `ledger-entries`, referenciando `contaId` + `tenant`), que é a opção que a skill recomenda para o que "cresce sem limite"; alternativa mais barata a curto prazo, mas só paliativa, é `$push` com `$each`/`$slice` para manter uma janela recente embutida e o histórico completo em coleção separada — dado que este é um ledger de cobrança (histórico financeiro que não pode ser descartado), a coleção separada é a escolha correta, não o `$slice` isolado.
