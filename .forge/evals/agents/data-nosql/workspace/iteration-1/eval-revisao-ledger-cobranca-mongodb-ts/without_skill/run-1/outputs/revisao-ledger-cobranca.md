# Revisão — persistência do ledger em `services/cobranca` (MongoDB, TypeScript)

Escopo: `services/cobranca/src/ledger/conta-repository.ts`, à luz do README (replica set de três membros — primário, secundário, árbitro). Revisão apenas — nenhum arquivo foi alterado; quem aplica é o task-coder.

## 1. Consistência

- **`registrarLancamento` grava com `writeConcern: { w: 1 }`.** Num replica set PSA (primário-secundário-árbitro), `w: 1` confirma só no primário; o árbitro não guarda dado, então uma falha de primário antes da replicação para o secundário perde o lançamento já "confirmado" ao chamador. Trocar por `writeConcern: { w: 'majority' }` (no caso PSA isso equivale a exigir o secundário também, já que o árbitro não referenda dado).
- **`transferir` usa `readConcern: { level: 'local' }` dentro de uma transação multi-documento.** `local` não dá isolamento de snapshot — a leitura do saldo de origem pode não refletir um commit concorrente ainda não replicado, abrindo janela de leitura suja dentro da própria transação. Trocar por `readConcern: { level: 'snapshot' }` (o padrão recomendado para transações no driver) combinado com `writeConcern: 'majority'`.
- **Saldo e histórico de lançamentos são atualizados por dois caminhos desconectados.** `registrarLancamento` só dá `$push` em `lancamentos` e `$inc` em `versao` — nunca toca `saldo`. `transferir` só mexe em `saldo` via `$inc` e grava uma linha em `movimentos` — nunca chama `registrarLancamento`. Não há transação nem invariante que amarre as duas trilhas; saldo e extrato podem divergir silenciosamente. Trocar por um único caminho de escrita: ou saldo é sempre derivado de `lancamentos`/`movimentos` (ledger como fonte da verdade, saldo materializado por agregação/projeção), ou toda mutação de saldo passa a gravar seu lançamento correspondente na mesma transação.
- **`transferir` não confere se a conta destino existe antes de creditar.** `updateOne({ _id: destino }, { $inc: ... })` não lança erro se não casar nenhum documento — `matchedCount`/`modifiedCount` não são checados. Um `destino` inválido debita a origem e o crédito desaparece. Trocar por checagem explícita de `matchedCount === 1` (ou `findOneAndUpdate` com `upsert: false` e validação do retorno) antes de confirmar a transação; abortar e lançar erro caso contrário.
- **Transação sem `try/catch/finally` nem retry de erro transiente.** Qualquer exceção entre `findOne` e o `commitTransaction` deixa a sessão aberta (nunca há `session.endSession()`), e não há o retry recomendado pelo driver para `TransientTransactionError`/`UnknownTransactionCommitResult`. Trocar por um wrapper padrão (`try { ...; await session.commitTransaction(); } catch { await session.abortTransaction(); throw; } finally { await session.endSession(); }`), com retry nos dois pontos (execução e commit) conforme o padrão oficial do driver MongoDB para transações.
- **Sem chave de idempotência em `transferir`.** Um retry de cliente (timeout, reconexão) reexecuta a função inteira e duplica débito/crédito; não há `idempotencyKey` único indexado para detectar reenvio. Trocar por um campo `idempotencyKey` (fornecido pelo chamador) com índice único em `movimentos`, checado/gravado dentro da mesma transação.

## 2. Dinheiro

- **Conversão de centavos para `Decimal128` passa por ponto flutuante:** `Decimal128.fromString((valorCentavos / 100).toFixed(2))`. A divisão `/100` é feita em `number` (IEEE-754) antes de virar string — para determinados valores de centavos isso arredonda errado antes mesmo de chegar ao `Decimal128` (o `Decimal128` fica exato a partir daí, mas a entrada já veio distorcida). Trocar por construção de string sem passar por divisão flutuante, ex.: `` `${Math.trunc(valorCentavos / 100)}.${String(Math.abs(valorCentavos) % 100).padStart(2, '0')}` `` (ou manter tudo em centavos inteiros também no `Decimal128`/no schema, evitando a conversão de unidade).
- **Duas representações de dinheiro convivem no mesmo serviço:** `Lancamento.valor` é `Decimal128`, mas `saldo` (em `transferir`) é incrementado como `number` cru via `$inc`, e o parâmetro de entrada é `valorCentavos: number`. Não há um único tipo de dado para valor monetário no repositório. Trocar por um padrão único — se a decisão é "inteiro de centavos", `saldo` deveria ser `number`/`Long` consistente e `Decimal128` não deveria aparecer só em `movimentos`; se a decisão é `Decimal128`, `saldo` também deveria ser `Decimal128` para evitar limite de precisão segura do JS (2^53) em somas acumuladas ao longo do tempo.
- **`valorCentavos` não é validado.** Nenhuma checagem de que é inteiro positivo antes de debitar/creditar — um valor negativo inverte a transferência, um valor fracionário corrompe a unidade "centavos". Trocar por validação explícita (`Number.isInteger(valorCentavos) && valorCentavos > 0`) antes de abrir a transação.
- **Não há dupla entrada (double-entry) real.** `transferir` grava uma única linha em `movimentos` com `origem`/`destino`, em vez de dois lançamentos (débito na origem, crédito no destino) que se poderiam conferir por soma zero. Combinado com o ponto de consistência acima (saldo dissociado de `lancamentos`), o ledger não tem uma trilha auditável única de onde o saldo é recomputável. Trocar por dois lançamentos por transferência (um em cada conta, mesmo `transferenciaId` correlacionando os dois), com saldo sempre derivável da soma dos lançamentos.

## 3. Multi-tenant

- **Nome da coleção é montado por interpolação direta da tenant: `` `contas_${tenant}` ``, sem validação/allowlist.** Isso é uma abertura para injeção de nome de coleção (caracteres especiais, `$`, `.`, barra) e para erro operacional silencioso (typo na tenant cria coleção nova em vez de falhar). Trocar por validação de formato da tenant (regex fixo, ex. `^[a-z0-9_]{1,40}$`) antes de montar o nome, ou preferencialmente abandonar collection-per-tenant (ver abaixo).
- **`movimentos` é uma coleção global, sem nenhum campo de tenant e sem filtro de tenant em `extrato`.** Diferente de `contas_${tenant}`, a coleção `movimentos` não carrega `tenant` no documento, e `extrato(contaId)` nem recebe `tenant` como parâmetro — a query é `{ origem: contaId }` sem qualquer escopo. Isso é uma inconsistência arquitetural grave: metade do dado é particionado por tenant, a outra metade não, e a função de leitura do extrato não tem como impedir que um `contaId` de uma tenant colida (ou seja usado deliberadamente) para ler movimentos de outra tenant. Trocar por: adicionar `tenant` a cada documento de `movimentos`, exigir `tenant` como parâmetro obrigatório em `extrato`, e filtrar por `{ tenant, origem: contaId }` (com índice composto `{ tenant: 1, origem: 1 }`).
- **Collection-per-tenant (`contas_${tenant}`) não escala.** MongoDB/WiredTiger degrada com milhares de coleções (mais arquivos abertos, mais pressão de cache, catálogo maior, startup mais lento); esse padrão cresce linearmente com o número de tenants. Trocar por uma única coleção `contas` com campo `tenant` indexado (índice composto `{ tenant: 1, _id: 1 }`), que escala independente do número de tenants e ainda permite sharding por `tenant` se necessário no futuro.

## 4. Crescimento de documento

- **`$push: { lancamentos: lanc }` em `registrarLancamento` cresce o array dentro do próprio documento da conta, sem limite.** Uma conta com uso contínuo ao longo de anos eventualmente esbarra no limite de 16 MB por documento do MongoDB, e mesmo antes disso cada `$push` fica mais caro (realocação/movimentação do documento no WiredTiger conforme ele cresce) e o documento inteiro precisa ser lido para qualquer operação sobre a conta, mesmo quando só o saldo é necessário. Trocar por lançamentos em coleção própria (`lancamentos`, um documento por lançamento, com `contaId`/`tenant` indexados) — o padrão de "bucket" (lançamentos agrupados por período, ex. um documento por mês/dia) é uma alternativa intermediária se o volume de leitura por conta for muito maior que o de escrita e a paginação por documento inteiro for aceitável.
- **Sem separação entre dado "quente" (saldo, poucos campos, lido a cada transação) e "frio" (histórico completo).** Embutir o histórico dentro do documento de conta faz toda leitura de saldo (`transferir` faz `findOne` na conta inteira) trazer o array de lançamentos acumulado, mesmo quando só o campo `saldo` é necessário. Trocar por manter no documento de conta só os campos operacionais (`saldo`, `versao`, `tenant`) e mover todo o histórico para a coleção separada citada acima — reduzido ainda mais com uma projeção (`{ projection: { saldo: 1 } }`) na leitura de saldo dentro de `transferir`.

## Resumo priorizado (para o task-coder)

1. **Multi-tenant / vazamento de dado:** `movimentos` sem campo `tenant` e `extrato` sem parâmetro `tenant` — corrigir antes de qualquer outra coisa, é o único item com risco de exposição de dado entre clientes.
2. **Dinheiro:** conversão via ponto flutuante em `Decimal128.fromString((valorCentavos / 100).toFixed(2))`, ausência de dupla entrada e de validação de `valorCentavos`.
3. **Consistência:** saldo e lançamentos atualizados por caminhos desconectados sem transação comum; falta de checagem de conta destino inexistente; falta de idempotência; transação sem try/catch/retry/endSession; `writeConcern: w:1` incompatível com a topologia PSA descrita no README.
4. **Crescimento de documento:** `lancamentos` embutido sem limite no documento de conta — migrar para coleção própria antes que alguma conta de alto volume esbarre no limite de 16 MB.
