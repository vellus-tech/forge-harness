# Armadilhas de build/test .NET (comandos de verificação)

Esta página não é sobre o scanner — é sobre o passo 2 do Protocolo (baseline de build) e sobre escrever/rodar teste .NET em geral, quando o resultado de `dotnet build`/`dotnet test` precisa ser confiável antes de revisar ou declarar pronto. Nenhuma destas armadilhas tem detector estático: cada uma só aparece ao rodar o comando, e o sintoma costuma ser ambíguo (zero testes, erro sem causa aparente) o suficiente para ser mal diagnosticado.

## `dotnet test` contra `.slnx` exige `--solution`, não aceita posicional

Em repositório migrado de `.sln` para `.slnx` (formato XML), `dotnet build Projeto.slnx -c Release` aceita o caminho como argumento posicional, mas `dotnet test Projeto.slnx -c Release` recusa com "A especificação de uma solução para 'dotnet test' deve ser feita por meio de '--solution'". A assimetria entre os dois subcomandos do mesmo CLI não é óbvia. Use sempre `dotnet test --solution <arquivo.slnx>` em repositório com `.slnx`, mesmo que `dotnet build` aceite a forma posicional para o mesmo arquivo — não assuma que a sintaxe que funcionou para `build` vale para `test`.

## `UseMicrosoftTestingPlatformRunner` exige `--project` e rejeita `--logger` em silêncio

Um projeto de teste com `<UseMicrosoftTestingPlatformRunner>true</UseMicrosoftTestingPlatformRunner>` (xunit.v3 + Microsoft.Testing.Platform, comum em repositórios novos em .NET 10) muda duas coisas que o hábito de `dotnet test` em projetos VSTest não prevê: (1) em alguns contextos de CLI, `--project <caminho>.csproj` deixa de ser opcional; (2) a flag `--logger "console;verbosity=detailed"` (sintaxe VSTest) não é reconhecida pelo runner MTP, e o comando retorna "Zero testes executados" com exit code 5 — sem erro de parsing, indistinguível de "suíte filtrada" ou "descoberta falhou". Antes de rodar `dotnet test` num projeto com essa flag, cheque o `.csproj` por ela e use só as opções documentadas pelo Microsoft.Testing.Platform; rode primeiro sem nenhuma flag extra para confirmar que a suíte é descoberta e executa, só então adicione opções. "Zero testes executados" com exit code 5 e nenhuma mensagem de erro anterior é sinal de flag incompatível com o runner antes de ser sinal de filtro ruim.

## `global.json` com `test.runner: Microsoft.Testing.Platform` não basta — cada `.csproj` precisa aderir

Declarar `"test": {"runner": "Microsoft.Testing.Platform"}` no `global.json` não migra sozinho nenhum projeto de teste: cada `.csproj` também precisa de `<TestingPlatformDotnetTestSupport>true</…>` (ou `<UseMicrosoftTestingPlatformRunner>true</…>`). Se apenas parte dos projetos de teste da solução aderiu, `dotnet test Solucao.slnx` falha em **todos** eles — inclusive no que está configurado certo — com "Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later", repetida por projeto, sem indicar qual projeto é a causa real. Ao medir cobertura após um merge ou mudança grande: (1) nunca aceite esse `rc` como prova de zero regressão — a mensagem fala de configuração do csproj, não de teste vermelho; (2) `grep -arn "TestingPlatformDotnetTestSupport\|UseMicrosoftTestingPlatformRunner" **/*.csproj` para achar quais projetos de teste ainda não aderiram ao MTP; (3) como contorno que não exige editar nenhum csproj, rode o apphost compilado de cada projeto de teste diretamente (`bin/<Config>/<tfm>/<NomeDoProjeto>`, sem extensão) — cada execução imprime um bloco `=== TEST EXECUTION SUMMARY ===` com `Total/Errors/Failed/Skipped/Not Run` por projeto, que é a prova de número real que CI verde sozinho não dá.

## `dotnet test` relata zero testes em silêncio quando `DOTNET_ROOT` não está setado

Em shell sandboxed/efêmero (tool de agente, CI runner) que não herda o profile de um terminal interativo, `dotnet test` (runner MTP) pode falhar ao lançar o apphost por projeto quando `DOTNET_ROOT`/`DOTNET_ROOT_ARM64` não estão setados e o SDK não está no caminho padrão do apphost (`/usr/local/share/dotnet`) — por exemplo um SDK instalado via Homebrew em `/opt/homebrew/Cellar/dotnet/<versão>/libexec`. A falha aparece só como "Zero testes executados", exit code 5, sem stack trace e sem qualquer menção a .NET ou apphost — fácil de confundir com filtro errado ou build desatualizado. `dotnet build` e `dotnet --version` funcionam no mesmo shell porque passam pelo muxer `dotnet` do PATH, que tem resolução de SDK própria, independente das variáveis do apphost; por isso um build limpo seguido de um teste "vazio" não aponta para a causa real. Quando `dotnet test` relatar zero testes com exit code 5 sem detalhe, rode o executável do apphost gerado diretamente (`./<projeto>/bin/<config>/<tfm>/<NomeDoAssembly>`, sem argumentos) no mesmo shell — se o SDK não for localizável, o apphost imprime uma mensagem explícita e acionável com os caminhos que tentou. Nesse caso, exporte `DOTNET_ROOT` (e `DOTNET_ROOT_ARM64` em Apple Silicon) para a raiz real do SDK antes de repetir `dotnet test`.

## `Testcontainers.PostgreSql` muda construtor por versão; `.editorconfig` CRLF × `.gitattributes` LF conflitam no gate de formatação

Copiar um padrão de teste (`new PostgreSqlBuilder("postgres:15-alpine").Build()`) de um projeto/repo de referência para outro, dentro do mesmo workspace, pode quebrar a compilação sem sinal prévio: o `Testcontainers.PostgreSql` expõe construtores diferentes por versão de pacote (uma versão não tem o construtor `PostgreSqlBuilder(string image)` que outra tem), e o erro só aparece no `CS1729` do `dotnet test`, sem relação óbvia com a causa. Antes de reaproveitar uma chamada de construtor copiada de outro projeto/repo, `grep -an "Testcontainers\." <csproj do destino>` para confirmar a versão pinada — versões diferentes do mesmo pacote num monorepo não são incomuns, mesmo entre projetos do mesmo repositório.

Separadamente: se o repositório tem `.editorconfig` com `end_of_line = crlf` mas `.gitattributes` normaliza o texto para LF no armazenamento (`*.cs text diff=csharp` sem `eol` explícito), todo arquivo já commitado está em LF no disco, mas `dotnet format --verify-no-changes` exige CRLF na árvore de trabalho — um arquivo novo escrito com LF (padrão de qualquer editor/API fora do Windows) falha o gate por `ENDOFLINE` em toda linha, mesmo com conteúdo semântico correto. Antes do primeiro `dotnet format --verify-no-changes` num arquivo novo, cheque `end_of_line` em `.editorconfig` e, se `crlf`, normalize o arquivo (`perl -i -pe 's/\r?\n/\r\n/' <arquivo>`) antes de rodar o gate pela primeira vez.

## `HttpClient` rejeita CRLF antes de enviar, mascarando o teste da defesa do SERVIDOR

Ao escrever um teste de host (`WebApplicationFactory`) para provar que o servidor neutraliza um cabeçalho HTTP malformado (CRLF, caractere de controle), montar a requisição via `HttpRequestMessage`/`HttpClient.SendAsync` falha de um jeito que parece sucesso: o `SocketsHttpHandler` valida cabeçalhos antes de enviar e lança exceção ao detectar CRLF — mesmo com `Headers.TryAddWithoutValidation`, que só pula a validação no momento de adicionar, não no de enviar. O teste nunca chega a exercitar a defesa do servidor; prova só que o cliente .NET tem a própria defesa. Quando o teste precisa provar uma defesa do **servidor** contra cabeçalho malformado, use `TestServer.SendAsync(Action<HttpContext> configureContext)` (via `factory.Server`) em vez de `HttpClient` — esse caminho manipula `HttpContext.Request.Headers` diretamente como dicionário, sem passar pela camada de transporte HTTP do cliente, então o valor malformado chega intacto ao pipeline real (roteamento, autenticação, model binding, controller). Regra geral: ao testar uma defesa contra entrada que normalmente seria bloqueada por uma camada de transporte, bibliotecas-cliente convencionais (HttpClient, navegador, SDK de qualquer linguagem) costumam ter a própria validação de protocolo, que intercepta o caso antes de chegar ao sistema sob teste — é preciso um caminho que bypasse essa camada.

## Mockar client gRPC gerado direto com NSubstitute, sem `Grpc.Core.Testing`

Para testar um adapter .NET que envia requisições via client gRPC gerado (`protoc-gen-grpc-csharp`) quando não há servidor fake gerado do mesmo `.proto` disponível (`GrpcServices="Client"` apenas), a classe de cliente gerada (`ClientBase<T>`) já foi desenhada para mock: construtor protegido sem parâmetros e métodos virtuais, então `Substitute.For<FooClient>()` funciona direto, sem precisar instalar `Grpc.Core.Testing` nem duplicar o `.proto` com `GrpcServices="Both"` só para o teste. Para o retorno, construa manualmente `new AsyncUnaryCall<TResponse>(Task.FromResult(response), Task.FromResult(new Metadata()), () => Status.DefaultSuccess, () => new Metadata(), () => {})` — o construtor é público em `Grpc.Core`. Capture a request enviada com `Arg.Do<TRequest>(r => captured = r)` nos parâmetros posicionais certos (request, headers, deadline, cancellationToken) da assinatura gerada.

## Raw string literal interpolado (`$"""..."""`) não aceita `{{}}` para escapar chave literal

String interpolada verbatim (`$@"..."`) escapa chave literal com `{{}}`; copiar esse mesmo escape por analogia para um raw string literal interpolado (`$"""..."""`, C# 11) produz `error CS9006` — a regra de escape de `{`/`}` em raw string literals interpolados é diferente da de string interpolada clássica e não é intercambiável por cópia visual. Ao converter ou copiar por analogia um template SQL/JSON entre um teste que usa `$@"..."` e outro que usa `$"""..."""`: ou mantenha o mesmo estilo de string do exemplo copiado (mais simples quando o literal tem chaves), ou, usando raw string interpolado com chave literal, aumente o número de `$` iniciais (`$$"""..."""` com `{{` significando uma chave literal) em vez de reaproveitar `{{}}` de memória. Prefira `$@"..."` quando o template tiver chaves literais e nenhuma razão forte para usar raw string literal.

## Teste de contador OTel estático via `MeterListener` precisa de `DisableParallelization`

Um helper de teste baseado em `MeterListener` (`SetMeasurementEventCallback` + `Start()` + capturar medições) só atribui corretamente uma medição ao teste atual se nenhum outro teste que toque o mesmo `Meter`/`Counter` estático rodar concorrentemente no mesmo processo — `MeterListener.Start()` escuta o instrumento no processo inteiro, não por call stack. Uma suíte que passa isolada (filtro numa única classe) e falha só quando roda junto de outras classes é o sintoma clássico: o contador não tem correlation id, então emissões concorrentes são indistinguíveis dentro do listener, e o padrão é fácil de confundir com "poluição de outra classe" quando a interferência é dentro da mesma classe, mesmo contador, threads diferentes. Toda classe xUnit que afirma sobre medições de um `Meter`/`Counter` estático via `MeterListener` precisa se colocar numa coleção com `[CollectionDefinition(nameof(<Nome>), DisableParallelization = true)]`/`[Collection(nameof(<Nome>))]`, mesmo copiando um exemplo existente que hoje passa — o exemplo pode simplesmente nunca ter rodado ao lado de classes suficientes para expor a corrida.
