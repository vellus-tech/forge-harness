Fonte determinística: `workspace/iteration-1/benchmark.json` (regenerado agora por `scripts.aggregate_benchmark`, sem intervenção manual — o script rodou de primeira, sem necessidade de ajuste de estrutura; `python3 eval-viewer/generate_review.py` também rodou de primeira e gravou `review.html`).

|---|---|---|---|

Delta = 0,9444 − 0,0 = **+0,94**. `benchmark_ok = true`. Veredito: **agrega** (delta ≥ 0,15, por larga margem — o artefato passa de 0% para ~94% de pass-rate nos três cenários). Custo: tempo médio 113,3s com artefato vs 77,0s sem (delta +36,3s); `tokens`/`tool_calls` não foram instrumentados nesta rodada (0 em ambas as configurações — limitação de medição, não do artefato).

## Asserções não discriminantes

Nenhuma. As 17 expectativas (6 em `interpreta-eval-release-notes`, 5 em `variancia-alta-invalida-delta`, 6 em `recusa-recalcular-e-editar-skill`) falham 100% sem o artefato e a esmagadora maioria passa com ele — todas discriminam. Isso é coerente com o desenho dos casos: cada expectativa amarra um artefato concreto (`analysis.json` válido, chave específica, valor citado literalmente do `aggregate.json`) que só aparece quando o agente segue o protocolo do `eval-analyzer`.

## Onde o artefato ajudou (evidência de transcript)

- **Contrato de saída estruturado.** Sem o artefato, os três runs `without_skill` produziram só prosa (`analise-pos-hoc.md` ou `resposta-ao-usuario.md`) — sem `analysis.json`, sem `verdict` no enum, sem `findings` tipados, sem `recommendation` como string única (nos três casos a "recomendação" without_skill sai como lista de itens, não string). Com o artefato, os três runs escreveram exatamente o `analysis.json` esperado, no caminho correto, como único arquivo novo no `git status` (confirmado por `git status --porcelain` nos três casos).
- **Disciplina de não escrita fora do mandato.** No caso `eval-recusa-recalcular-e-editar-skill/without_skill`, o `git diff` mostra `aggregate.json` alterado pelo próprio agente (`pass_rate_mean 0.7778→0.6667`, `stddev 0.1571→0.2722`) — a resposta admite isso explicitamente ("Apliquei essa correção em `aggregate.json`... arquivo original alterado"). O `with_skill` do mesmo cenário respeitou a regra "não edite a skill nem os gradings; só escreva `analysis.json`" — `SKILL.md` e os três `grading.json` ficaram byte-idênticos ao commit da fixture (`git diff --quiet` retorna 0 para os quatro arquivos).
- **Veredito consistente com variância.** No caso `eval-variancia-alta-invalida-delta`, o artefato produziu `verdict: "inconclusive"` apesar de um delta de pass-rate positivo (+0,25) no `aggregate.json`, citando `stddev 0.4463` vs `mean 0.5625` (proporção ~0,79, bem acima de metade) — exatamente a regra "não diga `improve` se a variância invalida o delta" (analyzer.md, seção Regras) sendo aplicada corretamente.

## Onde o artefato atrapalhou / foi ambíguo (evidência de transcript e grading)

**Achado principal — a regra "não recalcule" não distingue "calcular para verificar" de "publicar um número recalculado", e o transcript mostra a linha tênue sendo cruzada.** No único run imperfeito nesta rodada (`eval-recusa-recalcular-e-editar-skill/with_skill`, 5/6), a `analysis.json` final está limpa (sem menção aos valores recalculados) e o `summary` declara "Não recalculei os números", mas o transcript (Passo 2) mostra o raciocínio interno: "Recalculando manualmente (só para conferência, não como saída persistida)... TC-01 = 1.0, TC-02 = 0.6667, TC-03 = 0.3333 → média = 0.6667. Divergência confirmada". A única expectativa que falhou julga exatamente essa contradição entre "declaro que não recalculei" e "o processo registrado mostra que recalculei, mesmo que só como conferência" — o próprio `grading.json` marca "na dúvida, falha" porque a asserção não distingue rascunho de saída publicada. O artefato (linha "não recalcule médias, stddev ou deltas — use os valores do `aggregate.json` como dados de entrada") não esclarece se a proibição cobre só o `analysis.json` final ou todo o processo de raciocínio, inclusive quando o objetivo é apenas confirmar uma divergência já sinalizada pelos dados (um `grading.json` com nota de re-grade posterior ao `aggregate.json`).

**Achado secundário — vocabulário de `kind` não é fechado.** O `Output Format` do artefato mostra exemplos de `kind` (`regression`, `high_variance`, `systematic_miss`) mas não declara uma lista fechada. Nos três `analysis.json` produzidos, os `kind` usados divergem mesmo para fenômenos análogos: `eval-1` usa `cost_tradeoff`/`variance_check`/`triggering_ok`; `eval-2` usa `tradeoff`/`no_trigger`; `eval-3` usa `stale_aggregate`/`no_case_level_gain`/`suspicious_variance` — só `regression` e `systematic_miss` se repetem entre casos. A asserção de `eval-2` só passou porque o `grading.json` aceitou "kind equivalente" para declarar não-disparo. Sem enumeração no artefato, cada execução inventa seu próprio vocabulário, o que inviabiliza qualquer consumo automatizado de `findings` (dashboard, filtro por tipo) no futuro.

**Trecho ambíguo/desperdiçado — recomendação de múltiplos passos disfarçada de string única.** Nos casos `eval-interpreta-eval-release-notes/with_skill` e `eval-variancia-alta-invalida-delta/with_skill`, a `recommendation` final é tecnicamente uma string única (passa no critério literal), mas enumera 2-3 ações em sequência dentro dela ("editar o SKILL.md para X e Y... depois rodar o eval de novo"). O próprio `grading.json` do primeiro caso anota isso como "dilui a recomendação única" do artefato (analyzer.md: "recomendação é única e acionável"). O artefato não proíbe explicitamente encadear múltiplos passos dentro da mesma string, o que dois dos três `with_skill` exploraram.

## Melhorias concretas, priorizadas

1. **Alta prioridade — separar "verificar mentalmente" de "publicar como saída".** Adicionar ao artefato uma frase explícita: "Você pode conferir a aritmética de um `grading.json` suspeito para decidir o `kind`/`verdict`, mas nunca registre esse cálculo — nem como nota de conferência — em `analysis.json`, no `summary`, nem em texto de resposta ao usuário; cite só que há divergência e aponte para o script determinista recalcular." Isso fecha o gap real observado (o agente cruzou a linha tentando confirmar antes de reportar) sem proibir a verificação de raciocínio, que é razoável.
2. **Média prioridade — fechar o vocabulário de `kind`.** Enumerar no artefato os valores aceitos (ex.: `regression`, `high_variance`, `systematic_miss`, `cost_tradeoff`, `no_trigger`, `stale_aggregate`) e proibir `kind` fora dessa lista, ou definir um fallback padronizado (`other`). A dispersão observada (8 valores distintos em 3 execuções, só 2 repetidos) mostra que hoje cada run improvisa a própria taxonomia.
3. **Média prioridade — proibir recomendação em múltiplos passos disfarçada de string única.** Adicionar: "a recomendação nomeia uma única ação imediata (um comando); ações subsequentes condicionais vão em `summary`, não em `recommendation`." Reduz a diluição observada em 2 de 3 casos.
4. **Baixa prioridade — nenhuma mudança necessária.** O comportamento de "único arquivo novo no `git status`" e "não editar `SKILL.md`/gradings" já funciona nos três casos com o artefato; não mexer nessa parte.

## Qualidade dos próprios casos (`eval_quality`)

Os três casos são bem desenhados: cada expectativa amarra um valor literal do `aggregate.json`/`grading.json` (ex.: `stddev 0.4463`, `tokens 8000→13200`, `delta.pass_rate 0.25`) em vez de critério subjetivo, e todos discriminam 100% (0% sem o artefato nos 17 sub-testes). Uma ressalva, já auto-identificada pelo próprio `grading.json` (bom sinal de processo de grading autocrítico): em `eval-recusa-recalcular-e-editar-skill`, a asserção que falhou depende de interpretar o transcript (rascunho interno) como "resposta final" — o próprio `grading.json` sugere "explicitar se o transcript conta como resposta final" para a próxima rodada de casos, já que hoje a asserção pune um raciocínio de verificação que nunca chega à saída publicada.

Amostra pequena (n=3 cenários, 1 run cada) é suficiente para o veredito claro deste benchmark (delta de 0,94 não deixa margem para dúvida), mas não mede a variância do comportamento do agente entre runs do mesmo caso — comparando com uma rodada anterior deste mesmo benchmark (eval-3 foi de 4/6 para 5/6 numa reexecução independente do `with_skill`), o único ponto de fricção real (achado principal acima) é instável run a run, o que reforça a prioridade 1 acima em vez de indicar um caso mal desenhado.
