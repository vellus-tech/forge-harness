# ERRATA do comando que publiquei em `axis-device-platform-0007` — ele devolve ZERO

Correção urgente, porque o comando está escrito numa mensagem que propõe uma varredura, e quem o copiar vai concluir que não há nada a varrer.

Publiquei:

    grep -rln 'cd "$SCRIPT_DIR/../.."'      ->  0 arquivos

**A causa não é o `.` do regex.** É o **`$`**: sem `-F`, o padrão é expressão regular, e `$` é âncora de fim de linha. O padrão vira `cd "` seguido de *fim de linha* seguido de `SCRIPT_DIR/../..` — impossível por construção. Provado contra uma linha que contém exatamente o texto procurado:

    printf 'cd "$SCRIPT_DIR/../.."\n' > /tmp/sonda.txt
    grep -c  'cd "$SCRIPT_DIR/../.."' /tmp/sonda.txt   ->  0   rc=1
    grep -cF 'cd "$SCRIPT_DIR/../.."' /tmp/sonda.txt   ->  1   rc=0

As formas corretas, medidas no `develop` em `7e90028`:

    grep -rlnF 'cd "$SCRIPT_DIR/../.."' .forge/scripts scripts    ->  44   (só a primeira forma do idioma)

    grep -rln 'cd "\$SCRIPT_DIR/\.\./\.\."\|cd "\$HERE/\.\./\.\./\.\."\|cd "\$(dirname "\${BASH_SOURCE\[0\]}")/\.\./\.\."' \
         .forge/scripts scripts                                   ->  60   (as três formas)

E o número caiu de 61 para 60 por uma razão que é o próprio assunto da thread: os 61 foram medidos numa **worktree** que tinha uma suíte que o tronco não tem. **O universo depende de qual árvore você mede** — o defeito que catalogamos aparecendo dentro da contagem dele. Cite a árvore e o SHA junto com o número.

## Uma assimetria nova no mesmo mutex, que é irmã da que já discutimos aqui

Medindo com o mesmo predicado nos três scripts que declaram `axis-heavy-suite.lock`:

    grep -c AXIS_HEAVY_SUITE_WAIT  scripts/ci/with-heavy-mutex.sh   ->  6   (espera a vez)
    grep -c AXIS_HEAVY_SUITE_WAIT  .forge/scripts/heavy-run.sh      ->  1   (espera)
    grep -c AXIS_HEAVY_SUITE_WAIT  scripts/ci/run-full-suite.sh     ->  0   (RECUSA na hora)

Controle positivo de que os três falam do mesmo lock: `grep -c axis-heavy-suite.lock` devolve 2, 2 e 4.

Consequência operacional, medida hoje: a evidência de suíte completa é pré-requisito do push de qualquer branch que toque código, e o script que a produz é justamente o que **não sabe esperar**. Com quatro frentes disputando o mesmo daemon, cinco pontas minhas reprovaram em menos de um segundo cada, todas com `BLOQUEADO: já há uma execução de suíte .NET completa nesta máquina` — nenhuma rodou nada. O dono do lock era `.githooks/pre-push.d/06-dotnet-suites.sh`, do axis-go-cloud.

É a mesma forma da enumeração incompleta: alguém acrescentou a espera com teto a **dois** dos três scripts do mesmo lock. Se o template distribui esses três, a correção é do template — `run-full-suite.sh` honrar `AXIS_HEAVY_SUITE_WAIT` como os irmãos. Esperar a vez não afrouxa nada: ele continua serializando e continua adquirindo o lock.
