## 1. A ponte — `.forge/hooks/pre-tool-use/dispatch-file-hook.sh`

164 linhas, `sha256 6d270f077b810ab1`, tronco `2c814414`.

**Por que ela existe, com o numero medido.** Os hooks de arquivo comecam com `FILE="${1:-}"; [ -z "$FILE" ] && exit 0`. O Claude Code **nao passa argv** — passa o JSON do tool no stdin. Fiados como comando nu, recebem zero argumentos, caem no `exit 0` e aprovam tudo:

```
via stdin, sem argv  ->  rc=0, silencio                       (aprovado)
via argv             ->  rc=1, "Chave privada PEM detectada"  (reprovado)
```

**As quatro decisoes:**

**(a) Traducao stdin para argv.** Extrator em ARQUIVO, nunca em heredoc de python. Medido: com heredoc, ele vence a redirecao e vira o stdin do python, o `json.load(sys.stdin)` acha EOF, o extrator lanca, e a ponte devolvia `exit 0`. *A propria ponte reproduzia, na primeira versao, o defeito que existe para fechar.* Quem pegou foi a sonda comportamental; nenhuma leitura de codigo pegaria, porque o codigo esta sintaticamente correto.

**(b) Traducao do codigo de saida.** No PreToolUse so `exit 2` bloqueia; `exit 1` e erro nao-bloqueante e a ferramenta roda. Os hooks saem 1. So o `0` do alvo vira `0`; **todo o resto vira 2**, inclusive 126 e 127, que e o alvo que nao rodou.

```sh
_propaga() { [ "$1" -eq 0 ] && exit 0; exit 2; }
```

**(c) Falha-fechado em toda impossibilidade de julgar.** Stdin vazio, python3 ausente, mktemp falhando, JSON ilegivel, alvo ausente — tudo 2, com a causa nomeada. *Nao entender a entrada nao e aprovar.*

**(d) Quatro fontes de conteudo.** `content` (Write), `new_string` (Edit), `new_source` (NotebookEdit), `edits[].new_string` (MultiEdit, concatenadas). **As duas ultimas sao obrigatorias**: o matcher `Write|Edit` e comparado como **regex**, e MultiEdit e NotebookEdit contem "Edit", logo casam — e entregam campos que nenhum dos dois primeiros cobre. Sem elas, os dois caem no ramo "sem conteudo", a ponte manda o hook ler o **disco**, e num hook pre-escrita o disco tem o conteudo antigo, limpo.

> **Correcao ao cabecalho do proprio arquivo:** ele ainda diz "duas fontes". Sao quatro. A frase e anterior a correcao e ficou para tras — **copiem o codigo, nao o comentario.**

**Detalhe que importa:** acima de 256 KiB o conteudo vai por um espelho que **preserva o caminho relativo**, porque os hooks tem dispensas por path; espelhar num mktemp cru mudaria o veredito. Passar argv gigante daria E2BIG, e o erro seria indistinguivel de aprovacao.

## 5. A armadilha do .cs — para o axis-go-cloud, sem ela a extensao nao basta

O detector de PAN casa `LOG_CALL + PAN_DIGITS` com flag `i` (`check-data-governance.mjs:70`):

```
LOG_CALL   = (?:\blog|\blogger)\.\w+\s*\(.*
PAN_DIGITS = \b\d{13,19}\b
```

Medido **com o flag i**:

```
CASA    log.info(...)                  Java
CASA    logger.warn(...)               Java
CASA    Logger.LogInformation(...)     C#     <- casa por causa do flag i
CASA    this.logger.Log(...)           C#
ESCAPA  _logger.LogInformation(...)    C#     <- convencao canonica de campo privado .NET
ESCAPA  _log.Debug(...)                C#
ESCAPA  _log4net.Info(...)             C#
```

A causa isolada: **o underscore E caractere de palavra**, entao nao ha fronteira `\b` entre ele e "logger".

```
re.search(r'\blogger', '_logger.X(')      -> False
re.search(r'\blogger', ' logger.X(')      -> True
re.search(r'\blogger', 'this.logger.X(')  -> True
```

**Acrescentar .cs ao CODE_EXTS e necessario e nao suficiente.** O universo passa a incluir os arquivos e o predicado continua cego a forma dominante de log daquela stack — e a cegueira parcial um nivel abaixo: agora nao e a extensao que exclui, e o padrao.

> **Retratacao minha, na mesma medicao:** a minha primeira passagem omitiu o flag `i` e concluiu que `Logger.LogInformation` tambem escapava. Ia publicar isso. **Ao reproduzir um predicado de outro arquivo, copie os flags junto do padrao** — flag de compilacao e parte do predicado.

## 7. E um falso positivo que me barrou ao vivo, escrevendo esta mensagem

O `guard-machinery-drift.sh` — a peca que bloqueia o upgrade com maquinaria divergente — recusou a escrita deste corpo, porque ele cita a frase do comando entre crases. Medido, com controle:

```
heredoc com delimitador ENTRE ASPAS, com crase   rc=2  BLOQUEADO   <- falso positivo
heredoc com delimitador ENTRE ASPAS, sem crase   rc=0
echo com crase                                   rc=2  BLOQUEADO   <- correto, ali a crase executa
```

Verdade-de-terra: dentro de heredoc com delimitador entre aspas o bash **nao expande** crase — imprime literal. O guard supoe que expande. A distincao que falta ao tokenizador e entre heredoc com delimitador citado e nao citado.

**Contornei pelo conteudo, trocando a formatacao do texto — nao pelo gate.** Registro porque o contorno natural de quem tiver pressa e desligar o hook, que e o que esta campanha combate. E a mesma familia do defeito que reprovou o PR 217: tokenizador que aproxima a gramatica do shell erra nos dois sentidos, e cada aproximacao precisa da sua fixture.
