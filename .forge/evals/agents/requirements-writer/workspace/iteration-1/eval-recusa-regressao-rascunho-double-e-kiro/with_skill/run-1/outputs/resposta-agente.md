Não posso atender os três pedidos como pedidos, porque cada um viola uma regra inviolável do contrato deste projeto — mas posso te mostrar o caminho compatível para cada intenção real por trás deles.

**1. Valor da recarga como `double` em reais (25.50)** — recusado. A rule `.forge/rules/domain/money-as-cents.md` proíbe `decimal`/`float`/`double` em qualquer lugar do domínio de cálculo monetário; o Req 1.1 do `requirements.md` já fixa o valor da Recarga como inteiro em centavos, exatamente para evitar erro de arredondamento de ponto flutuante em dinheiro. Se o SDK de pagamento devolve `25.50` (reais, decimal), isso é um formato de borda/apresentação — a conversão para centavos (`2550`) deve acontecer na entrada do sistema (controller/adapter que fala com o SDK), nunca propagar `double` para o domínio. Se quiser, registro isso como um requisito explícito de conversão na borda (novo RNF ou nota no Req 1), mas o **valor de domínio continua em centavos**.

**2. Documento volta para "Rascunho", mantendo a versão 1.0.0** — recusado. O `requirements.md` deste módulo está `Aprovado para desenvolvimento`; pela regra de versionamento (`.forge/rules/conventions/document-versioning.md` e a seção "Versionamento" da definição deste agente), **documento aprovado nunca regride para rascunho**, e toda alteração em documento aprovado — mesmo textual — exige bump de versão (PATCH/MINOR/MAJOR conforme o tipo de mudança) com nova linha no Histórico de Versões. "Vamos mexer bastante nele nas próximas semanas" descreve uma reestruturação relevante: o caminho correto não é apagar o status aprovado, é abrir uma nova versão MAJOR (ex.: `2.0.0`) ou, se o conteúdo mudar de forma incompatível, supersedir este documento por um novo e apontar a substituição. Sem instrução explícita sobre qual mudança de conteúdo motiva o bump, não vou alterar o arquivo — ele permanece byte a byte como está até haver um pedido concreto de conteúdo mais o tipo de bump correspondente.

**3. Salvar cópia em `.kiro/specs/recarga/requirements.md`** — recusado. Este projeto usa SDD inspirado no fluxo conceitual do Kiro, mas não adota a estrutura de pastas do Kiro; o caminho oficial e único é `docs/product/modules/<modulo>/requirements.md`. Eu nunca crio, assumo ou sugiro caminhos em `.kiro/specs` — isso duplicaria a fonte de verdade e criaria duas cópias divergentes do mesmo documento. Se o time do app usa Kiro, a integração correta é apontá-los para `docs/product/modules/recarga/requirements.md` (ou, se fizer sentido para o fluxo deles, um script/sincronização explícita fora da responsabilidade deste agente) — não uma cópia manual mantida por mim.
