## Frontend UI Review — portal-web / src/features/settings (UI-231)

Gates determinísticos:
  [FAIL] A0 fonte da verdade   — não localizada. Não existe `tokens.css`/`colors-and-type.css` em nenhum lugar da árvore, `node_modules` não existe e `@acme/design-tokens` (declarado em `package.json`) nunca foi instalado nem vendorizado. Sem a lista de tokens definidos, não há como distinguir token real de token fantasma.
  [N/A]  A1 phantom-tokens     — bloqueado por A0. `SettingsPage.css` referencia 8 custom properties (`--surface-raised`, `--text-primary`, `--border-subtle`, `--radius-lg`, `--space-6`, `--shadow-sm`, `--text-heading`, `--font-size-xl`); nenhuma pôde ser confirmada como definida no DS.
  [OK]   A2 hardcoded-color    — 0 ocorrências (`rg` sobre `src/`, excluindo tokens/testes/stories)
  [OK]   A3 fallback-literal   — 0 ocorrências (`var(--x, #hex)` não aparece; todos os `var()` são referência nua)

  [N/A]  A5 cobertura          — não avaliável; sem o repositório/tokens completos não há como varrer a superfície inteira do app, só a feature isolada

Achados semânticos (severidade · arquivo:linha · recomendação):
  - HIGH · `src/features/settings/SettingsPage.css:1-9` · Todos os 8 tokens referenciados dependem de `@acme/design-tokens`, que está declarado em `package.json` mas nunca instalado (`node_modules` ausente) nem vendorizado (nenhum `tokens.css` no repo). Isso é exatamente o cenário que a skill chama de "contrato que não existe, mascarado por ausência de fallback": aqui não há fallback literal (A3 OK), o que é bom, mas também não há como provar que o contrato do outro lado — a definição do token — existe. Visualmente pode estar perfeito hoje e ainda assim ser 8 tokens fantasmas amanhã. Recomendação: antes de fechar UI-231, instalar as dependências (`npm ci` ou equivalente) e rodar `scan-phantom-tokens.py` contra o `tokens.css` real; só então A1 tem resultado.
  - MEDIUM · `src/features/settings/SettingsPage.test.tsx:7-9` · Os três testes (`renderiza`, `aplica a classe do card`, `aplica a classe do título`) verificam apenas presença de texto e nome de classe (`toHaveClass`), nunca valor computado de estilo. "Testes todos verdes" não é evidência de padronização — é exatamente o padrão do incidente que motivou esta skill (2174 testes verdes convivendo com buracos de dark mode). Recomendação: adicionar assert de `getComputedStyle` sobre `--surface-raised`/`--text-primary` em light e dark, mais um teste de round-trip de tema.
  - INFO · Fase B (verificação visual light↔dark) não executada — não há build/dev server rodável neste ambiente (sem `node_modules`) nem captura de tela disponível. Pendência registrada, não é aprovação implícita.

Veredito: BLOQUEADO — A0 (fonte da verdade dos tokens) não pôde ser estabelecida, então A1 (o gate mais importante da skill) não pôde rodar. A ausência de cor hardcoded e de fallback literal (A2/A3 OK) é necessária mas não é suficiente: o CSS pode estar 100% "limpo" na forma e ainda assim referenciar 8 tokens que nunca existem no design system. "Os testes estão todos verdes" não muda esse veredito — os testes só verificam estrutura, não estilo computado (Fase D). Não recomendo fechar o ticket UI-231 até: (1) instalar `@acme/design-tokens` e localizar/gerar o `tokens.css` real; (2) rodar A1 (`scan-phantom-tokens.py`) contra ele e confirmar 0 tokens fantasmas; (3) verificar visualmente light↔dark (Fase B); (4) reforçar os testes para exercitar estilo computado, não só estrutura (Fase D).
